# LLM Personality Board — notes for Claude Code

A grid of cards, one per LLM, each with: monogram, name, "live"/"Archived"
badge, a short description (self-generated by the model), a six-axis
HEXACO radar chart with an uncertainty band, and a version combo to browse
past runs of that model. This is not a mock-data POC: a real pipeline
administers the questionnaire to models via API and persists results in a
SQLite DB, alongside content pages (about / methodology / questionnaire /
considerations) and a bilingual (EN/IT) UI.

The project is public on GitHub under AGPL-3.0 — see [`README.md`](README.md)
for the user-facing overview and [`CONTRIBUTING.md`](CONTRIBUTING.md) for how
to contribute, including AI-assisted contributions.

## Tech stack

- **Frontend**: Next.js 14 (App Router) + React 18, TypeScript.
- **Radar chart**: hand-drawn SVG in `components/RadarChart.tsx` (polar →
  cartesian coordinates on 6 axes), no charting library.
- **Persistence**: SQLite via `sql.js` (WASM, no native build step) in
  `lib/db.mjs` — see below.
- **LLM providers**: `@anthropic-ai/sdk`, `openai` (also reused for xAI/Grok
  and DeepSeek, both OpenAI-compatible), `@google/generative-ai`.
- **i18n**: custom, no library — locale resolved from the browser's
  `Accept-Language` header, no manual switcher. See `lib/i18n/`.
- **Hosting**: Vercel — live at https://progetto-psycochat.vercel.app.
- **Source**: public GitHub repo, AGPL-3.0.

## Data model (`lib/hexaco.ts`)

```ts
interface ModelScore {
  name: string;
  monogram: string;
  hue: number;
  scores: [number, number, number, number, number, number]; // 0-100, H,E,X,A,C,O order
  oneLiner: string;       // English self-interpretation (always generated in English)
  oneLinerIt?: string;    // Italian translation of oneLiner, added afterwards — may be absent for old/unbackfilled runs
  dominant: string;
  margin?: [number, ...]; // half-width of the uncertainty band per domain
  source: "live" | "fake";
  isCurrent?: boolean;    // false if a newer version of this model exists
  model?: string;         // exact provider model string, only if source="live"
  assessedAt?: string;    // ISO timestamp of the run, only if source="live"
}
```

`H, E, X, A, C, O` = Honesty-Humility, Emotionality, Extraversion,
Agreeableness, Conscientiousness, Openness (fixed order everywhere, from the
DB to the radar chart).

## Persistence (`lib/db.mjs`)

Single-file SQLite DB (`data/psychochat.sqlite`, **tracked in git** — see
"Deployment" below for why), two tables:

- `assessments`: one row per `(model_name, assessed_at)` run — same shape as
  `ModelScore` plus `item_means` (per-item mean across repeats) and
  `one_liner_it`.
- `assessment_item_repeats`: one row per `(model_version, assessed_at, item,
  repeat)` with the raw 1-5 answer — full fidelity behind the means above.
  Keyed on `model_version` (the actual run, e.g. `"gemini-3.5-flash-lite"`),
  not `model_name` (the family, e.g. `"Gemini"`).

`is_current` is a stored fact, recomputed on every write: the row with the
"highest" `model_version` for a given `model_name` wins (`isNewer`, which
compares by version rank first, then `assessed_at`) and is shown as "live";
the rest become "Archived", regardless of which run was actually most recent
chronologically.

`versionRank` (used by `isNewer`) extracts the first number in a
`model_version` string, treating **both `.` and `-` as the minor-version
separator** (e.g. `claude-opus-4-5` → `4.5`, `claude-fable-5-1` → `5.1`) —
this matters because providers mix conventions (`gpt-5.2` vs
`claude-opus-4-5`); getting this wrong silently ties versions that should
rank differently (a real bug fixed once already — see git history).

`getHomeData()` is the entry point `app/page.tsx` uses: one DB open serving
both the grid (latest run per model) and every model's version list, so the
per-card combo has its options prefetched instead of lazily fetching
`/api/versions` on first click (that lazy fetch used to cause a visible
delay — sql.js WASM init + parsing the whole file from scratch is the
expensive part, worse on a cold serverless instance).

`recomputeIsCurrentForModel(modelName)` forces an `is_current` recompute
without writing a new row — needed once after a `versionRank`/`isNewer`
logic change, since existing rows' `is_current` was persisted under the old
logic.

`lib/db.d.mts` types `lib/db.mjs` — **must be named `.d.mts`, not `.d.ts`**,
to actually pair with a `.mjs` source under this project's
`moduleResolution`. A `.d.ts` sibling here is silently ignored and
TypeScript falls back to inferring types straight from the untyped JS
(this happened once — cost a debugging session to find).

`data/mock-scores.json` and `data/history/*.json` are pre-SQLite-migration
state (`scripts/import-to-db.mjs` imported them once) — untracked in git,
kept on disk only as a historical archive, not read by the app anymore.

## Assessment pipeline (`scripts/assess.mjs`, `npm run assess`)

Administers the real IPIP-HEXACO item bank (240 items, public-domain analog
of the HEXACO-PI-R) from `items/sample/json/items.sample.json` to one real
model per configured provider in `MODEL_CONFIG`, and writes each run
directly to the DB via `upsertAssessment`. Not a validated psychometric
administration: it's a pragmatic proxy (each item asked `ASSESS_REPEATS`
times at temperature 1; the spread across repeats stands in for a
confidence band).

Things to keep in mind when touching this script:

- Items are grouped into batches of `ASSESS_BATCH_SIZE` (default 40) to cut
  round-trips, shuffled across domains so the model doesn't anchor on
  consecutive same-domain answers.
- Every provider has its own "reasoning token" traps that can eat the whole
  output budget before producing visible text (o1/o3/o4/gpt-5 families,
  Grok's high default `reasoning_effort`) — see the comments on
  `isReasoningModel` and `makeXaiClient`.
- `ASSESS_ONLY=ModelName` limits the run to a subset of models; others stay
  untouched in the DB.
- A model with no configured API key, or excluded via `ASSESS_ONLY`, doesn't
  abort the whole run — it's just skipped with a warning.
- At the end of each model's run, one extra call generates a
  self-interpretation one-liner (the model describes itself in light of its
  own scores) instead of a templated sentence — avoids similar-scoring
  models producing the same boilerplate.
- A second extra call **translates** that English one-liner into Italian
  (`translateToItalian`) — a plain translation, not a second independent
  self-assessment, so the two language versions always say the same thing.
  Only re-translated when the English sentence actually changed.
- Provider ids with a trailing release-date stamp (e.g.
  `claude-opus-4-5-20251101`) are stripped of that suffix before being
  stored as `model_version` (`displayModelVersion`) — it's needed to call
  the API but just widens the version combo for no informational gain over
  the `4-5` already in the name. The full dated id is always what's
  actually sent to the API.
- `scripts/translate-onliners.mjs` is a one-off backfill for
  `one_liner_it` on rows assessed before that feature existed.

Before running a new provider model version at scale, worth a quick sanity
probe first (one minimal API call) — model catalogs churn: some ids get
deprecated for newer API keys (404 "no longer available to new users"),
some are transiently overloaded (503 "high demand," usually recovers with
the built-in retry).

## Internationalization (`lib/i18n/`)

Locale is resolved from the browser's `Accept-Language` header
(`resolveLocale`, `lib/i18n/locale.ts`) — **not** a separate URL per
language (no `/en`, `/it` paths), no manual toggle, no cookie. Resolved once
per request in `app/layout.tsx` and shared to client components via React
context (`useLocale()`, `lib/i18n/context.tsx`).

Known limitation: since there's no distinct URL per language, a crawler
only ever indexes whichever language it requests with (typically English) —
full bilingual SEO indexing would need path-based locale routing, which is
a bigger change than this app currently does.

`lib/i18n/dictionaries.tsx` holds shared UI chrome strings (home page, card
badges, nav links). `/methodology`, `/considerations`, and `/questionnaire`
keep their own `TEXT`/locale-keyed content colocated in their page files
instead, since they're long-form rich JSX (links, `<strong>`, `<code>`) —
splitting that into a shared dictionary would add indirection without much
reuse.

Card descriptions (`oneLiner`/`oneLinerIt`) are the one piece of
user-visible content that's LLM-generated rather than hand-translated — see
the assessment pipeline section above.

## SEO (`lib/seo.ts`, `lib/site.ts`, `app/sitemap.ts`, `app/robots.ts`)

`lib/site.ts` centralizes `SITE_URL` (from `NEXT_PUBLIC_SITE_URL`, falls
back to a placeholder) and `GITHUB_URL` — every SEO-facing surface reads
from here instead of hardcoding a domain. `lib/seo.ts`'s `buildMetadata()`
is used by every page's `generateMetadata()` for consistent
canonical/Open Graph/Twitter card fields. `app/opengraph-image.tsx` and
`app/icon.svg`/`favicon.ico`/`apple-icon.png` are the social preview image
and favicon set (static files under `img/favicon/` for reference — Next.js
picks up the ones directly under `app/` by convention).

Title/meta description copy is built around reasoned candidate keywords
(no real search-volume data — no keyword tool access), not verified market
research.

## API routes (`app/api/*`)

- `GET /api/models` → `listLatestPerModel()`, one `ModelScore` per model
  (the one with `is_current = 1`).
- `GET /api/versions?model=X` → available runs for one model (only used as
  a fallback refresh path now — `app/page.tsx` prefetches this for every
  model upfront via `getHomeData()`).
- `GET /api/assessment?model=X&assessedAt=Y` → one `ModelScore` for that
  `(model, assessedAt)`; missing/empty `assessedAt` = seed entry.

## Version combo (`ModelCard.tsx`)

Not a native `<select>`: a native popup can flip open upward past the
card's top edge and paint over the radar chart/one-liner above it. It's a
custom listbox (`VersionCombo`), anchored below the trigger only, with its
panel height clamped via JS to whatever room is actually left in the
viewport (scrolls instead of overflowing). The caret is an inline SVG
chevron (`.comboCaret`, 10×10px, 1.6px stroke) — a plain `▾` text glyph
looked too small/thin to notice regardless of `font-size`, since fonts
render it with a lot of built-in padding around the actual triangle.

## Deployment (Vercel)

Two gotchas that cost real debugging time, worth knowing before touching
deploy config:

1. **`data/psychochat.sqlite` is intentionally tracked in git**, despite
   being generated data. Vercel's serverless functions have no persistent
   writable filesystem — the committed file is what actually ships as the
   live site's data. This is a stopgap until this moves to a real hosted
   DB; until then, updating live data means: `npm run assess` locally →
   `git add data/psychochat.sqlite` → commit → push (or `vercel --prod`).
2. **`next.config.mjs`'s `outputFileTracingIncludes`** forces
   `node_modules/sql.js/dist/*.wasm` into the deployed function bundle.
   `sql.js` is kept external to the webpack bundle (see the adjacent
   comment — its UMD wrapper breaks otherwise), which means the `.wasm`
   file is loaded via a plain runtime `fs` read that Vercel's build-output
   file tracer can't see on its own. Without this, every route touching
   the DB 500s in production with `ENOENT ... sql-wasm.wasm`.

`next build` (unlike `next dev`) fails on ESLint errors, including
`react/no-unescaped-entities` in JSX prose — ran into a backlog of these in
`/methodology` and `/considerations` blocking a deploy; fixed with
typographic quotes (`’ “ ”`) instead of straight ones. Watch for this in
new long-form content.
